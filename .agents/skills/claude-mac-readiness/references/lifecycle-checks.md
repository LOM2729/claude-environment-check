# 更新后复查、主动网络验证与启动前检查

执行顺序只按 [五步流程](five-step-setup.md)。本模块提供参数与证据边界；[生命周期验收](recovery-and-acceptance.md) 默认只有正常使用属于本次必需，其余七类事件列后续复查，未实测仍显示未完成，不为补齐报告主动重启／断网。

需要重启代理客户端/核心/服务或机器时，由客户手动操作；可能中断当前 Codex/远控通道的网络动作或影响不明的重载也交给客户。先保存进度和离线恢复说明，等待客户恢复连接后重新核验，不能自行断开通道；集中批准不替代人工交接。 具体按 [客户手动重启与恢复](five-step-setup.md#客户手动重启与恢复) 执行。

自动配置先按 [五步顺序](five-step-setup.md) 与 [统一 IPv4 策略](unified-ipv4.md) 执行。

这三个流程复用已批准的配置和本机基线。客户报告始终只有**已完成 / 未完成**，未完成写原因和下一步；不把探测超时、进程存在、文件匹配或启动请求成功当作完整验收。

## 如何接入客户服务

- 网络配置已读回后可保存首次启动所需的私有基线；客户端功能仍未验证，业务验收后再完成交付记录。系统语言继续保持；基线是比较材料，不是恢复旧设置的授权。
- 本包流程执行订阅刷新、客户端或核心更新后，Codex 读取/导出**当前活动配置**并运行 `recheck`。软件在外部自行更新时，下次服务或启动前再复查。本版没有安装常驻守护进程或后台计划任务。
- 主动探测先准备具体计划，向客户说明准确站点、路径、发送内容和可能暴露的出口，再按当前有效授权运行。已批准的同一范围不重问；新增站点、直连探测、STUN、地址族或断网实验不能隐含加入。
- 用户要“检查并启动 Claude/ChatGPT/Codex”时，运行本轮 `preflight`。必需项有未完成就停止启动；全部满足后才可按明确请求加 `--launch`。没有启动请求时只检查。
- 配置、基线、节点名、客户端路径、完整出口和 DNS 地址属于私有材料，仅留在客户机。转交客户只发脱敏报告；每位客户使用原始发布包。

## 更新前、更新后首次联网与更新后验收

更新涉及的证据按三个时点保存。更新前核对现有默认阻断、代理／TUN／节点／DNS 和必保业务例外能否覆盖更新及新程序首次联网；来源、目标版本和安装方式纳入具体方案。更新后首次联网前，盘点实际包内主程序／Helper、包外 Code 运行时与 Cowork 服务的准确身份及路径，比较新旧组件、签名／包身份、服务、接口和生效策略。完成后再验实际需要的功能和路径，建立新基线，旧材料保留。

普通 Claude 程序目录变更不应被直接解释为整机出站模式失效，当前有效默认阻止、全部 Allow 及例外条件仍须读回。代理核心路径、节点地址／端口、网卡／TUN、程序／服务／包或安全条件变化时，重核相应项。新增 Helper 或包外运行时覆盖不明时保持未完成，旧规则存在与开关 ON 只说明对应状态。

规则更新先保留旧保护和精确原值，在独立批次创建获准的新规则，逐项核对持久与有效策略的数量和完整条件。部分创建或读回失败只处理本批准确变更，保留回执；完整验证后才撤销已批准的旧规则。实际重启、换网、证书变更和业务观察分别取证，原生策略读回不代填它们。

## 先配置 DNS，再验证服务

新建或修复环境按两条线推进：

- 网络线：本机只读检查 → 配置 DNS/DoH、代理接管与规则 → 读回当前设置 → 获准的非 AI 目标诊断及解析器/代理路径核验 → 记录本轮证据 → Claude/OpenAI 服务验证。
- 本机独立线：时间准确性、客户指定时区、语言/地区等检查与已批准调整可同时推进，系统语言保持不改。自动配置／完整搭建的时区目标按 [时区策略](timezone-policy.md) 提出并核对；具体城市／时区 ID 未确定时先保留原值、补问目标，语言未给目标则保留。不同任务不要同时写同一配置或争用重启/重载。

DNS 尚未完成时，不访问、解析或用浏览器/CLI 探测 Claude/OpenAI 域名。旧参考文档中的服务连通命令也应后移；不要为了拿一个“修改前结果”先请求 AI 服务。读取文件、准备候选、读系统状态不需要等待网络线。

本工具约束本次新发起的诊断请求；不会自动关闭已运行程序，也不能追溯阻断其现有通信。

## 1. 保存与复查基线

使用本 Skill 的 `scripts/claude_setup.py`，命令中的路径由 Codex 现场填写。Windows 使用原生 Python/PowerShell；WSL 状态不能充当 Windows 宿主证据。

```text
python <Skill>/scripts/claude_setup.py baseline --policy domestic-v4 --config <当前活动配置的本地读回> --ai-original <ai-route计划目录>/original.bin --node <指定节点名> --executable <客户指定客户端入口> --out <新私有基线目录>
python <Skill>/scripts/claude_setup.py recheck --baseline <私有基线目录> --config <本次活动配置的本地读回> --executable <同一客户端入口> --out <新报告目录>
```

`--ai-original` 指向生成 AI 专属规则前的原配置；通常为 `ai-route` 输出下的 `plan/original.bin`。如自定义组名，创建基线时另传同一 `--group`。可用 `--format yaml|json|shadowrocket`。新增的其他配置修改应先完成差异核验，再生成对应 AI 候选和基线，不能把不相符的原文件混用。

基线包含当前配置和 AI 原配置的私有快照、哈希、机器绑定摘要、所选客户端入口/主程序/应用元数据摘要、可读取的系统设置和 DNS 配置身份。可加 `--browser-preferences <实际偏好JSON>`：只比较语言、DNS、WebRTC、代理相关字段，忽略无关运行计数；后续复查传同一参数。它不是组织策略或浏览器运行状态证明。

复查会发现配置改变/丢失、客户端主程序更新、已有系统字段变化、DNS 配置变化。DNS 地址在内存中形成摘要，公开报告不含原始地址；Mac 比较 scutil 可读配置，Windows 比较接口上的 DNS 配置。未取得的字段保持未验证。未覆盖的系统加密 DNS 策略、浏览器组织策略、应用辅助程序或私有更新文件仍需实际检查。

**发生变化时不自动回滚。** Codex 用 `plan` 或本地差异工具比较旧快照与本次文件，解释变化，保留客户后续调整。确认是合法更新并复测后，在新目录建立新基线，保留旧目录供追溯；不能修改旧哈希来“让检查通过”。哈希用于完整性比较，不是签名或新授权。

文件相同不能证明客户端已载入。每次必须核对当前 profile、规则模式、合并/覆写后的实际配置，不能反复拿旧导出文件复查。软件没有可读取的运行时入口时，现场核验单独标未完成。

## 2. 主动网络验证

先生成计划，不联网：

```text
python <Skill>/scripts/claude_setup.py network-plan --proxy http://127.0.0.1:<实际HTTP或mixed端口> --output <新计划.json>
```

默认生成 `bootstrap` 计划，仅包含 `example.com` 的系统 DNS 诊断及经指定代理请求 `https://www.cloudflare.com/cdn-cgi/trace`，不含 AI 服务域名。先完成本机 DNS/代理配置及读回，再按批准范围运行这些非 AI 诊断。请求会向对应站点发送普通请求/查询及其可见的出口信息，不发送账号 Cookie、Token、登录凭据或客户文件。

计划由 Codex 根据具体范围编辑并展示；不让客户手改 JSON。默认出口 `expected_ip` 为 null：第一次探测可以取得出口，但一致性仍为未完成。根据已核对的指定节点和运行中连接证据，在本地确认预期出口，再重测。出口变化不能自动改成新的预期值。

**同一 HTTP 端口不等于同一出站组。** 默认的 `www.cloudflare.com` 不在 AI 专属域名目录；AI 走节点 A、普通国外走节点 B 时，这个探针可能测到 B。必须结合实际规则/连接证据确定该检测站点对应的节点，再填写它的预期地址；不能把 B 的结果当成 AI-ONLY 出口证明。需要验证 AI 节点出口时，先准备并批准能够确实走该节点的探测路径；本工具不会偷偷添加检测站点分流规则。

客户批准具体非 AI 诊断计划后：

```text
python <Skill>/scripts/claude_setup.py network-check --plan <计划.json> --allow-network --out <新报告目录>
```

完成本次读回及真实路径核验后，由 Codex 记录已取得的证据；以下标记是**记录已经做过的检查**，不能为了通过而直接填写。仅看到 DNS 设置存在、Fake-IP 或一次解析成功均不够。非 AI 测试须能验证所需解析器及路由；不同域名策略不能互相冒充。证据不足时保持未完成，继续独立本机项目。

```text
python <Skill>/scripts/claude_setup.py dns-ready --config <本次活动配置读回> --proxy http://127.0.0.1:<已核验端口> --ipv6-interface <已关闭的实际服务/适配器> --readback-verified --dns-path-verified --proxy-path-verified --evidence <已取得的脱敏路径证据> --output <新的核验记录.json>
python <Skill>/scripts/claude_setup.py network-plan --phase service --proxy http://127.0.0.1:<实际端口> --output <服务计划.json>
python <Skill>/scripts/claude_setup.py network-check --plan <服务计划.json> --dns-ready <核验记录.json> --config <同一活动配置读回> --allow-network --out <新服务报告目录>
```

如检查浏览器网络偏好，记录和使用时均传 `--browser-preferences <实际偏好JSON>`。v2 记录要求即时读回明确的 IPv6 接口均已关闭；多个接口重复 --ipv6-interface，v1 记录需重新核验。记录有效期 30 分钟，绑定本机、已核验的本机代理入口、当前代理配置、可读系统 DNS 身份、网络相关状态及所选浏览器网络字段；DNS/代理变化、切换代理端口、缺失或过期都会停止服务请求；服务计划不能混用未核验的入口或改走直连。时区、系统语言、浏览器语言变化不使网络记录失效，可以独立推进。preflight 仍如实报告这类漂移为未完成，但不把它列为网络/启动的阻断项；实际时钟错误导致 TLS 失败时仍由网络检查拦截。

`service` 默认包含 Claude/OpenAI 的 HTTPS 验证及相关 DNS 查询。工具在每项服务请求前复核记录；不满足时尚未发送的项目全部记未完成。旧版无 phase 的计划按 service 处理，不能绕过前置检查。bootstrap 计划混入已知 AI 域名（包括 DNS/STUN 主机）时整份计划在任何探测前拒绝。目录仅覆盖已核对域名；不能把伪装别名或新域名塞进诊断阶段。

记录只证明操作者登记了什么及本机设置是否一致，不是工具自动证明 DNS 路径正确，更不提供联网授权；实际请求仍需当前有效的范围批准和 --allow-network。需要重新核验时不自动修改旧记录或放宽条件。

每项探测在独立子进程中执行，单项总时限 9 秒、最多 12 项。不自动重试或跳转，不读取 `.curlrc`、不继承环境代理选择，也不在代理失败时回落直连。HTTPS 校验证书和主机名；需要企业 CA 时先按客户实际信任配置处理，不能关 TLS 验证。

| 探测类型 | 计划字段和路径 | 证据边界 |
| --- | --- | --- |
| `https` | `url`、`route: proxy/direct`；代理仅接受显式本机 HTTP/mixed 端口；`expected_statuses` 为允许的 2xx | 仅证明该路径 TLS/HTTP 响应。301/302 不跟随；401/403/挑战页不自动算功能通过。登录、模型请求、上传和 WebSocket 另验 |
| `egress` | 同 HTTPS；`response_format` 为 `ip`、`trace` 或 `json_ip`，`expected_ip` 为本地已确认地址 | 取得地址与匹配预期是两件事；只匹配当前探测路径，不证明客户端采用 |
| `dns` | `host`、`family: auto/ipv4/ipv6`，走本机系统解析器 | 取得地址仅证明有解析结果；不证明上游 DNS 在代理内，不覆盖 TYPE64/65 查询、DNS64 或浏览器 DoH |
| `stun` | 明确 `host`、`port`、`family: ipv4/ipv6`、预期出口；走原生 UDP，依靠实际 TUN/路由接管 | 会向指定服务器发 UDP 并暴露该路径出口，默认不启用。验证响应事务及格式，但不是浏览器 WebRTC/ICE 测试 |

`family` 对直连 HTTPS 可选 IPv4/IPv6。显式 HTTP 代理的目标地址族由核心决定，工具不能强制或据此证明代理的 IPv6 路径，计划中只能为 auto。需要验证 IPv6 必须在批准范围里设计对应路径，不能为了检测偷偷发直连请求。

每项有唯一 `id` 和布尔 `required`，用于“是否阻断启动”。客户确认不适用的检测才从计划移除；不能为了通过把失败的必需项改成非必需。可选项失败仍显示未完成。服务计划默认只有系统 DNS 解析为补充检测；系统 DNS 配置身份复查仍属于启动必需项。

**STUN 无响应一律不能证明零泄漏。** 可能是服务不可达、DNS 失败、链路丢包或 UDP 被阻断。要证明阻断，需有实际策略/流量证据和有效对照；工具不会在超时时自动记完成。原生探针也不能代替实际浏览器的 WebRTC 检查。

结果目录包含 `report.json`、离线 `report.html`、`report.md`，以及可能含完整 IP 的 `evidence.private.json`。公开报告只列状态、原因、下一步、检查时间和启动必需标识，不嵌入远程资源。

### 新版教程的 TUN 与故障取证补充

[2026-11-12 教程](https://x.com/suyuan1711/status/2120856418131820670)列出 11 项检查及三种断网场景，按本轮需要选用，真实客户端与故障效果均待目标验证。先区分显式代理请求、普通用户依赖 TUN 的请求和核心到上游的外层连接。核 TUN 时只对测试子进程清除代理环境覆盖，并核对相当于 `--noproxy '*'` 的路径选择，保留系统和其他进程的原环境；明确对应的进程身份与日志关联。

来源 PF 提示词只限制非 root 程序，root 请求不能代替所选普通用户的阻断观察，也不能据其通过扩称全机全部身份已覆盖。curl 7／28、HTTP 错误或无响应继续记录实际原因，需有原先可达对照和关联流量／规则证据。三个随机 DoH 子域及第三方 DNS API 仅说明相应样本，查询日志、DNS 上游和其他客户端分别核对。

| 选中的故障 | 分开保留的观察 |
| --- | --- |
| 海外节点失效，TUN 仍在 | 指定流量未落到 DIRECT 或其他未批准节点，已批准国内例外按预期工作 |
| TUN 消失 | 所选普通用户确实尝试连接，观察系统层拒绝或旁路，记录尚未覆盖的协议和身份 |
| 客户端退出 | 记录 GUI、核心与后台服务谁真正停止，不能仅关窗口；核对故障期路径和恢复后的实际功能 |

三种场景分别记录健康基线、故障开始／结束、尝试、阻断或旁路及恢复证据，每项恢复并核实后再进入下一项。受影响的 DNS／IPv6、旧连接和管理通道另核。可能中断当前控制通道的动作仍按手动交接处理，来源的整段自动演练要求不提供本轮执行授权。

### 名单每日更新验收

本节核对 [通用海外分类与每日更新](proxy-import.md#通用海外分类与每日更新) 的实际配置和数据，当前仅收录方法，目标设备的首次下载、定时更新、异常回退和路径效果均待验证。

| 事件 | 本轮应取得的证据 |
| --- | --- |
| 首次采用 | 三份源的格式／名称／路径／下载出站匹配，实际有效缓存已加载且非空，最后可用版本及摘要可定位 |
| 间隔维护 | 实际 provider 配置为 `86400` 秒，并记录最近尝试、最后成功、条目／摘要与加载状态，区分未变内容和请求失败 |
| 海外优先级 | 活动合并规则中海外分类在国内名单前，AI／遥测保护和拒绝／UDP／批准例外顺序仍满足方案，代表请求关联到实际规则和同一指定节点 |
| 休眠／离线／源延迟 | 保存数据年龄与失败原因，醒来或恢复网络后按实际刷新结果核对，旧缓存仍可用与已经更新分别报告 |
| 下载／解析异常 | 有效旧缓存、空／坏文件、首次无缓存分别处理，核内存与磁盘版本和最后可用快照，恢复后再核规则与业务 |

规则集更新时间或 HTTP 成功只支持相应下载观察，实际加载和路由继续分别读回。动态名单可在配置文本未变时改变行为，更新摘要变化后复查受影响的代表域名、国内业务、DNS 和控制通道，保护不受影响的既有证据。故障注入和恢复演练仅在本轮明确选择且独立救援已就绪时进行。

## 3. 启动前检查与可选启动

```text
python <Skill>/scripts/claude_setup.py preflight --baseline <基线目录> --config <本次实际配置读回> --executable <客户端入口> --network-plan <已确认服务计划.json> --dns-ready <本轮核验记录.json> --allow-network --out <新报告目录>
```

该命令每次重读本机基线、配置、客户端和设置，再执行本轮必需网络检测，不接受旧报告替代。启动方案至少需要同一显式代理下的必需 AI HTTPS 检查及带已确认预期 IP 的出口检测。直接访问其他站点成功不能代替。

用户明确要求启动时加 `--launch`。在发出请求前再次检查本机状态；探测期间发生变化则不启动。仅支持 Mac/Windows 原生执行端，启动目标必须来自本次命令参数并与本机基线相符，不执行导入 JSON 中的路径、shell 命令或任意参数。

- **Mac**：支持 `.app` 路径，核对 Info.plist 和主程序，再调用系统 `open`；也支持本机原生可执行入口。
- **Windows**：使用明确的原生可执行文件路径；不通过 `.lnk`、批处理或 PowerShell 脚本启动，不修改执行策略。若 Store 应用只能通过特殊协议启动，先完成检查，由 Codex 在已批准的本机界面启动并验证，不猜启动命令。
- **WSL/远程**：不能替代宿主机执行或启动；转到客户 Windows/Mac 原生环境。

启动/激活请求发出后，“客户端实际启动与采用”仍显示未完成。Codex 必须查看实际界面、认证与业务请求，再记录验收。已运行的客户端可能只是被激活，用户从其他入口启动也不会被该命令拦截；当前进程、浏览器、后台任务及远端需分别核验。

**本功能是一次启动前检查，不是持续 Kill Switch。** 不安装守护进程、防火墙或计划任务，不终止现有进程，不保证检查与启动之间不存在竞态。探针使用的代理路径不自动成为被启动应用的代理配置，仍需确认应用自身采用。需要持续断网保护时单独设计、授权和验收。

退出码：0 表示本轮必需检查满足（补充项目仍可能未完成）；2 表示有必需项未完成；1 表示输入、权限或操作错误。查看报告，不能只看退出码认定客户环境全项完成。身份不符或基线损坏时不能信任该基线，重新核对来源。若 --launch 返回操作错误，启动结果可能未知：先查看应用/进程和本地启动意图记录，再决定是否重试，不能盲目重复启动。
