# 给客户搭建 Claude 环境：执行流程

自动配置顺序以 [五步流程](five-step-setup.md) 为准。网络及选定接口 IPv6 未核验前，不打开/安装/登录 AI，不运行未证明离线的 CLI 诊断，不重启浏览器恢复标签。代理校验/导入/启用/重载前先检查测速、health-check、资源下载及附加请求。纯本机时间/语言字段检查可并行。

适用于“给客户搭环境”“按清单检查”“拿配置文件导入 Clash／小火箭”。先向操作者展示 [现场清单](../assets/customer-checklist.md)，再按目标设备实际情况执行。局部故障只展开受影响项目。完整服务包含时区、语言的只读记录，是否修改由客户需求决定。

## 先确定本次交付

复用已有信息，缺少时只补：目标电脑及系统、实际需要的浏览器／Desktop／Code、代理软件及已有文件、期望分流范围、是否远控及独立恢复方法。已有账号无需重走注册购买流程。

- **只有文件**：可做离线审查、准备候选、解释差异；导入、运行和网络效果均待目标机验证。
- **客户机终端／授权界面可用**：在客户机读取现状、准备并应用具体已批准变更、复测。服务者本机测试不能代替客户机。
- **资料／清单任务**：产出操作步骤即可，不顺带执行设备扫描或网络探测。

把路径写清楚：目标程序 → 本地代理入口／TUN → 中转（如有）→ 最终出口 → 服务。客户的 VPS 若只是出口，不等于 Claude 在 VPS 上执行。WSL、VM、容器、远端和后台任务按实际使用分别记录。

## 顺序与完成条件

| 顺序 | 要做的事 | 本阶段完成条件 |
| --- | --- | --- |
| 1 基线 | 版本、实际执行位置、现有可用功能；当前配置、选择组、模式、系统代理／TUN、自启状态 | 知道正在用哪一份配置、哪些客户端、哪些入口；未知项列出 |
| 2 时间与语言 | 系统自动校时、时区标识及自动时区、系统地区与语言、浏览器菜单与网页首选语言、浏览器报告的时区 | 原值已记录；目标不明确时保留原值；需要改的按对应平台语言模块执行 |
| 3 文件与备份 | 按 [导入与分流](proxy-import.md)识别文件、保留原配置及独立恢复步骤，生成最小候选 | 候选可解释、可解析、无不明脚本／远程转换，备份已读回 |
| 4 导入与启用 | 导入正确客户端，检查激活配置、核心解析、实际选择节点和规则模式；按需开启已批准接管方式 | 文件存在、导入成功、被选中、核心载入分别记录；载入失败先恢复已知可用配置 |
| 5 路由 | 比较业务、认证、内容加载、国内站点、LAN／企业 VPN、远控路径及规则优先级 | 目标请求命中预期规则／出站；明确直连、代理、阻断及故障回退范围 |
| 6 DNS | 分开系统解析、代理解析、浏览器 DoH、节点 bootstrap；检查 A／AAAA／TYPE64／TYPE65 | 实际查询及响应范围有记录，DNS 路径与配置目标一致；不足则待验证 |
| 7 IPv4／IPv6／UDP | 分应用、地址族、外层／目标侧检查；区分 QUIC、STUN、代理传输 | 只对观察到的路径下结论，不把 IPv6 超时、AAAA 为空当作全面阻断 |
| 8 浏览器 WebRTC | 所用浏览器和 Profile 的策略、候选类型及同地址族公网路径；必要时检查通话功能 | 有效检测与失败来源分开；无候选只记受限；修改后功能可用 |
| 9 Claude 功能 | 网页、Desktop、Code 各自验证登录／认证来源、正常请求；按用途验证附件、Artifacts、MCP／扩展等 | 以实际任务结果验收；401／403／429 单独分诊，不直接当作封号 |
| 10 持久化与交接 | 自启、配置合并和订阅更新影响；经另行批准再做故障／重启／换网实验 | 清单、差异、验证范围、未测项、恢复方法已交付；不承诺持续监控 |

修改先准备具体差异，按 [确认协议](change-confirmation.md)复用已有明确批准清单；不因换章节重复索要同项批准。对外检测采用已告知且批准的站点清单，具体数据流见 [检测说明](score-check.md)。故障演练单列，不能断开唯一远控通道。

## DNS：分层查，不用一个开关代表全部

1. **系统层**：Mac 从当前网络服务的“详细信息 → DNS”及 `scutil --dns` 核对；Windows 从实际适配器 DNS 与 `Get-DnsClientServerAddress` 核对。VPN、分域解析和企业域名也要保留。输出先脱敏，别把完整内网配置抄进交付。
2. **代理层**：核对生效配置的解析器、节点域名解析、业务 DNS 分流、备用解析器、Fake-IP／真实 IP，以及 DNS 请求本身的出站。节点解析依赖自身隧道可能形成引导循环。TUN 的 53 端口接管不代表接管 DoH／DoT。
3. **浏览器层**：Chrome／Edge 的“隐私与安全 → 安全 → 使用安全 DNS”（标签随版本变化）及有效管理策略；确认是否自带 DoH。系统 DNS 设置不能代替浏览器路径证据。需要调整时，优先修改造成冲突的一层，保留企业管理策略。
4. **实测层**：在已同意的解析器和测试域名上比较查询类别、RCODE、有无答案、超时及实际客户端连接。浏览器检测页的解析器地理位置、单次 `dig` 或命令退出成功都不能单独证明无旁路。

### TYPE64、TYPE65 与 DNS64

| 名称 | 含义与应检查内容 | 调整及验证边界 |
| --- | --- | --- |
| A / AAAA | IPv4 / IPv6 地址记录；核对谁解析、答案类型及连接实际采用的地址族 | AAAA 为空仅是该次解析结果，缓存、字面 IPv6、其他解析器仍可能参与 |
| TYPE64 / SVCB | 服务绑定记录 | 核对代理核心是否支持／过滤，以及浏览器是否绕过该核心解析 |
| TYPE65 / HTTPS | 用于 HTTP 的服务绑定记录，可携带协议和地址提示；可能用于 HTTP/3、ECH 等协商 | 不是端口 65，也不是跟踪器；过滤可能损失性能或隐私功能，不默认关闭 |
| DNS64 | 从 A 记录合成 AAAA，常与 NAT64 配合服务 IPv6-only 网络 | 不等于 TYPE64；移动网络或 IPv6-only 环境可能依赖它，关闭前确认连接依赖 |

**依据：** [RFC 9460](https://www.rfc-editor.org/rfc/rfc9460.html)、[RFC 6147](https://www.rfc-editor.org/rfc/rfc6147.html)。

Mihomo 的 [DNS 官方文档](https://wiki.metacubex.one/en/config/dns/)描述了上游附加参数 `disable-qtype-<int>`，例如 `disable-qtype-65`；这不是可随意粘贴的顶层 YAML 键。`dns.ipv6: false` 只控制该 DNS 层的 AAAA 答案，不能等同操作系统禁用 IPv6。需要过滤时先核对实际核心版本、具体解析器和作用范围，再展示修改及代价。

Shadowrocket 社区 Wiki 提及 `[General]` 中 `allow-dns-svcb` 与 `allow-dns-all`。这是**第三方技术资料**，不能视为 Anthropic 要求；两项共同配置、优先级和版本行为应以当前软件说明和实测确认。不要只抄默认值，也不要为过滤两种记录而把其他记录类型一并关闭。若软件内无法核实，保留为待验证，不猜参数。

若 Mac 已有 `dig`，可在批准的域名和解析器上分别查询 `TYPE64`、`TYPE65`；显式 `@服务器` 查询与浏览器解析不是同一路径。Windows 的 `Resolve-DnsName` 对类型支持依版本而异，先看帮助，不假装旧命令能测 HTTPS RR；不支持就使用已有可信解析工具或获准的诊断，不为此自动安装工具。查询没有答案也可能只是该域名未发布此记录，不能直接声称过滤成功。验证过滤需有已知可返回该类型的对照，且保留 A／AAAA、登录和页面加载回归结果。

## IPv6、WebRTC 与 UDP

- IPv6 分为系统接口、本机到代理入口、节点外层传输、节点到目标、浏览器候选五处。客户选择“仅 IPv4”时必须说明具体覆盖层；仅 `curl -4`、IPv4 回环端口或关闭 DNS AAAA 均不足以证明目标侧强制 IPv4。没有需求或故障证据时不全机关闭 IPv6；保护可能依赖 IPv6 的节点与企业网络。
- WebRTC 按实际浏览器、Profile、页面来源和有效策略检查；Chrome 可在 `chrome://policy`、Edge 可在 `edge://policy` 只读核对已生效的管理策略，不把普通设置页没有开关解释为已禁用。区分私网／mDNS、服务器反射公网候选和 TURN 中继；与同地址族、同路径的出口基线比较。公网候选不同是调查线索，不直接等于本地真实 IP 泄露；无候选、701 或超时为检测受限。
- 确认需限制 WebRTC 时，核对该浏览器版本支持的非代理 UDP 策略、代理自身 STUN 选项和作用范围；先预览其对通话／屏幕共享的影响，不为了测试变绿伪造候选地址，不默认安装扩展或授予麦克风权限。改后同浏览器复测并检查客户需要的媒体功能。协议依据：[RFC 8828](https://www.rfc-editor.org/rfc/rfc8828.html)。
- QUIC 常用 UDP/443，STUN 和媒体可以使用其他端口；屏蔽 UDP/443 不等于控制全部 WebRTC。部分代理上游本身依赖 UDP，不能一刀切禁用 UDP。核对不支持 UDP 时是拒绝还是 DIRECT，以及代理链每一段的行为。

Claude Code 的本地代理入口应按 [官方网络配置](https://code.claude.com/docs/en/network-config)核对 HTTP(S) 代理支持；上游是 SOCKS5 不等于可以把 SOCKS URL 直接交给 CLI。优先核对现有代理客户端的 HTTP／mixed 入口及实际端口，CLI、Desktop、后台启动来源分别验证，不改变客户节点凭据。

## 验收与恢复

每项保留四层：**配置声明 → 应用载入 → 目标进程采用 → 端到端观察**。记录时间、设备／浏览器／进程、版本、配置修订、预期与实际；上一层通过不自动填满下一层。用户自述、静态配置、模拟测试、目标机实测分别标注，依据类别见 [来源核对](evidence-sources.md)。

正常连接通过后，按任务选择节点失效、GUI 退出但核心仍在、核心停止／TUN 消失、休眠唤醒、换网、重启、订阅／客户端更新。每个实际演练必须有新连接尝试和有效观察，保留未测项；网站本来就不可达或整机断网不能证明故障阻断。已批准恢复时，仅撤回本次变更；当前内容若已被客户或订阅更新修改，先核对冲突，不能把旧文件整份覆盖回去。

交付四样：现场清单、已应用差异、分客户端测试结果、可离线执行的恢复说明。配置更新／换网／换浏览器／启动方式变化后，只复验受影响项。没有真实 Windows 或客户端导入验证时明确写出，文档与语法检查不能替代真机验收。
