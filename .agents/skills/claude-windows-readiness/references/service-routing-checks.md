# Claude 专属分组、规则优先级与拓展资料吸收

适用：Mac/Windows 的默认 `domestic-v4` 配置、Clash/Mihomo 与小火箭导入后的验收，以及网页正常但 CLI/桌面异常的排查。按 [五步流程](five-step-setup.md) 执行；本文件不改变 DNS/代理前置条件、客户手动重启、系统语言保留或已完成/未完成报告。

## 1. 专属分组与统一出口同时成立

默认基础组 `AI-ONLY` 继续服务 OpenAI、配套共享主机与普通国外流量；新增 **`AI-ONLY-Claude`**，让目录中已知 Claude 第一方域名的适用请求优先进入这个组。两组都只有同一个客户指定的本地具体节点，没有 DIRECT、自动测速、备用节点或嵌套选择器。Mihomo 组继续声明禁用目标侧 UDP；小火箭采用原生 select 与 UDP 拒绝/回退设置。**分组不同是为了辨识和验收，不是另选一个出口。**

组名由 `--group` 派生为 `<基础组名>-Claude`。修改基础组名时，生成、审计和基线命令必须保持一致；Codex 根据真实界面说明，不让客户手工改 JSON。现有无关同名组不能直接覆盖；发现同名、损坏管理块、两组绑定不同节点或未知链时停止该项，准备明确方案。

Claude范围由原目录与本轮社区补充共同构成，包括 `claude.ai`、`claude.com`、`anthropic.com`、`clau.de`、内容/MCP后缀及离线分类展开；共享服务也纳入同一指定节点，具体匹配范围见 [教程覆盖表](tutorial-coverage.md)。这个分类不是永久完整功能清单，也不代表所有共享主机只属于某一家。

旧 v0.9 单组候选可通过精确识别的管理块迁移；重复执行不叠加组和规则。已有基线不会因为新版本默认行为改变就自动被接受：准备差异、按本轮目标确认后导入并建立新基线。`unified-v4`、`ai-only` 是旧兼容策略，不把它们的旧排序当作当前默认。

## 2. 验收的是最终运行配置，不是文件排版

| 检查 | 必须取得的结果 |
| --- | --- |
| 实际路由模式 | 使用规则模式，不能在 Global/Direct 模式下凭文本顺序宣布生效 |
| 最终合并顺序 | 当前活动配置里的 Claude/其他 AI 保护块处于最前；再处理 IPv6/已保留明确拒绝、国内视频、其余 UDP、普通国内/本地及国外兜底 |
| 保护块内部 | AI 目标 UDP 拒绝 → 对应单节点组 → 同域名拒绝保护；不因节点缺 UDP 支持而继续落到后面 DIRECT |
| 分组实际成员 | Claude 专属组与基础组都仅绑定同一指定具体节点；核对 GUI 当前选择与运行连接链 |
| 已有拒绝/例外 | 如果原企业拒绝与 AI 目标冲突，先说明冲突，不能把允许规则无条件移到它之前。生成器拒绝无法确认的情况 |
| 持久化 | 从实际导入副本/有效覆写读回；订阅、全局扩展、GUI设置或更新不能悄悄抢在新规则前面 |
| 初始化就绪 | 核心端口监听不等于预期非空规则提供者已经载入；用客户端状态、日志或现有受控本地接口确认规则库就绪，再发送业务验证。仍初始化时等待或记未完成，不为检查新增对外控制接口 |
| 真实采用 | 在网络就绪后，分别查看 Claude、OpenAI及普通国外的连接链和实际功能；同名节点不保证供应商对每个目的地使用同一公网 IP |

使用 `ai-route --policy domestic-v4` 准备候选；导入后运行 `verify` 与同参数的 `ai-audit --policy domestic-v4`，再做目标机功能核验。静态匹配不能证明 TUN退出、系统代理旁路、旧会话和全部第三方功能都被保护。故意让节点失败须有具体授权和可用恢复通道；不能关闭唯一控制通道来演练。

初始化顺序的本包观察：Mihomo v1.19.32 的合成 loopback 测试中，监听器先于两个 inline provider 启动。测试因此核对已预期非空的两份规则库再发首个业务请求，不以重复业务请求掩盖失败；这不替代客户软件版本的实际验收。

规则机制依据：[Mihomo 规则优先级及 UDP 后续匹配](https://wiki.metacubex.one/config/rules/)。生成器/小火箭格式的结果按本包测试及当前软件分别验证，不能拿 Mihomo 核心通过代替小火箭运行验收。

## 3. 按教程完整扩展，并逐项核验

本轮按用户选择，以 Net.Coffee 域名页及11项配置页为基准补充默认 `domestic-v4`，详细目标、逐项执行点、官方机制与社区建议见 [教程覆盖表](tutorial-coverage.md)。旧 `ai_domains.json` 作为兼容目录保留，新补充范围单独管理与审计；不能只检查旧目录就断言覆盖完整。

扩展包含教程列出的共享后缀、精确CDN／认证主机、`sentry`／`datadog`／`sift`关键词、IPv4兜底与离线分类／ASN展开。它们会影响其他匹配的应用流量，具体差异必须进入预览，均保持客户指定节点和失败保护。IPv6仍拒绝；NTP域名的TCP采用同节点、UDP遵守当前拒绝策略，不能宣称已经配置UDP NTP代理。分类及ASN使用随包快照，不在客户首次运行时下载未知数据。`no-resolve`控制IP类规则是否触发目标解析，不是反向DNS防泄漏开关。

社区清单的配置选择与其因果解释分开记录。“NTP返回系统时区、代理NTP可以隐藏时区”的解释不成立：[RFC 5905](https://www.rfc-editor.org/rfc/rfc5905.html)描述的是与UTC的时钟同步，系统时区属于另一层。正常校时与UDP限制的兼容性仍需核对；未实现的UDP校时明确写未完成及下一步。

按实际网页、Desktop、Claude Code、MCP／插件、网关或云提供商核对功能，再依据 [Claude Code官方网络说明](https://code.claude.com/docs/en/network-config)与脱敏连接记录补查。完整纳入本轮教程不代表永久覆盖未来全部域名，不把社区列举的每个目标都称为核心必需。

## 4. 网页可用但 CLI 不行：查实际进程

- Claude Code 官方说明支持 HTTP/HTTPS 代理、不支持 SOCKS 代理。核对客户实际 HTTP/mixed 监听入口，不能只填一个 SOCKS 地址。
- 检查小写/大写代理变量的冲突，以及 `NO_PROXY` 对通配或 AI 域名的绕过。当前官方列出读取优先顺序 `https_proxy`、`HTTPS_PROXY`、`http_proxy`、`HTTP_PROXY`；只读私有比较必要来源，不回显带凭据的代理 URL 或整个环境表。存在变量不等于目标进程已采用，也不能仅由 NO_PROXY 推断 TUN 最终路径。
- Shell 中的变量在启动时读取；已经运行的会话不会因后来改 shell 自动更新。GUI、终端、后台工具和 WSL 的继承关系分别核对。需要重建目标会话时，先满足当前网络门槛、保存工作与批准范围，不结束当前 Codex/远控控制通道。
- 如果实际使用网关、Bedrock/Vertex/Foundry等接入，不能把它当直连 Anthropic 域名故障。检查实际提供商和认证来源，不运行凭据助手读取密钥，也不为排错关闭 TLS 验证。

以上是官方产品机制与本地诊断方法，不是“固定指纹即可防封”的结论。

## 5. 服务状态和 Windows 修复分支

发生超时/5xx等问题时，按当前联网阶段、批准范围与有效路径查看 [Claude 官方状态](https://status.claude.com/) / [OpenAI 官方状态](https://status.openai.com/) 的对应组件与事故时间；第三方监控只作额外线索。状态页请求同样遵守门槛，不能为查状态提前放行新 AI 访问。状态正常不证明客户路径正常；有事故时保留症状和观察，不反复重装或乱切出口。

Windows 桌面应用打不开时：区分原生/WSL/网页/CLI，先保存工作、只退出目标应用；有“设置 → 应用 → 已安装的应用 → 高级选项 → 修复”入口时才使用。某些安装方式没有该入口。不得自动重置、清登录资料或终止所有 node/python/代理进程；修复后再按门槛启动并验证实际功能，不能仅因出现对勾就判成功。程序身份或相关设置变化时，审阅漂移再确认新基线。依据：[Microsoft 应用修复](https://support.microsoft.com/en-us/windows/apps/repair-apps-and-programs-in-windows)。Mac 使用其实际客户端的对应诊断，不照搬 Windows 按钮。
